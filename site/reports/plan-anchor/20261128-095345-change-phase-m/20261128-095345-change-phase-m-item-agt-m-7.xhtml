description
After this sprint, adding a provider or a model is a line of configuration and no Rust change. The compiled-in table becomes the default configuration value, so today's behaviour is the default and every row can be overridden or added to. Settings become one typed struct, so adding a setting is adding a field, and serde does the validation that 150 lines do by hand today. The sprint deletes more than it adds.
## Deliverables
1. M7-1 sc-agent-config typed settings and provider/model rows: apply the corresponding verbatim inventory/change section in design.
2. M7-2 Update sc-agent-py provider_keys to read the configured provider entries in place of the deleted PROVIDERS table, preserving the Python result shape (REQ-SAG-0401, REQ-SAG-0503, ADR-SAG-0005).
- Architecture placement: `sc-agent-config` is a layer-1 crate.
+ Architecture placement (ANC-021; ADR-SAG-0004 v0.5.0): configuration changes land in `sc-agent-config`, layer 1, the lowest shared layer for typed settings and provider/model rows because every launcher needs the same configuration rather than its own Rust provider table.
+
+ The `jev` default selects the newest Jev model unless configuration sets another default (ANC-001); defaults contain no hard-coded local-model row, and local-model URL and model id come only from configuration (ANC-022). Related configuration values flow together as the same typed `Settings` struct rather than repeated method parameters (ANC-008). Any tests changed here drive their logic with controlled inputs and do not depend on races, wall-clock timing, sleeps, event-loop ordering or system load (ANC-017).
